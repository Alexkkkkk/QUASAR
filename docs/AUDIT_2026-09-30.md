## Findings
### F-30-01 — Build-hash snapshot drift (fixed)
`docs/build-hashes.json` no longer matched the artefacts produced by the current
sources. Regenerated with `npm run hashes:build`; the release gate must run from
the regenerated file.

### F-30-02 — Underfunded `transfer` failed in the action phase (fixed)
`receive(TokenTransfer)` paid the receiver `internal_transfer` (0.02 TON) and the
`FeeTransfer` leg (0.05 TON) out of the wallet's own balance without first
checking that this account could fund them. TEP-74 requires the opposite:
a wallet that cannot guarantee its outgoing value "must immediately stop
executing the request and throw error". An explicit compute-phase guard now
rejects such requests.
Source: TEP-74, "Should be rejected if … there is no enough TON".

### F-30-03 — `FeeTransfer` bounce left the pending ledgers dirty (fixed)
`bounced(bounced<FeeTransfer>)` restored the jetton balance but kept
`pendingResponseFees` / `pendingResponses` / `pendingResponseReceivers` entries
for that query id, so a settled-looking record survived a leg that never landed.
The bounce now clears all three records for the query id.

### F-30-04 — Fee legs are funded by the wallet, not by the inbound value (open)
The residual of the inbound message stays on the sender wallet instead of being
forwarded with mode 64 and refunded by the receiver. Behaviourally safe today
(0.075 TON floor), but it differs from the reference implementation and should be
restructured with a dedicated regression test before mainnet.
### F-30-05 — `scripts/deploy.js` is a compatibility shim (no change required)
`scripts/deploy.js` is an 18-line entry point that spawns `scripts/deploy_all.ts`
through `tsx` and holds no deployment logic of its own; no `package.json` script
references it. It is kept only for the historical `node scripts/deploy.js`
invocation and can be deleted once that call path is dropped.
