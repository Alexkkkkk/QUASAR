## Findings
### F-30-01 — Build-hash snapshot drift (fixed)
`docs/build-hashes.json` no longer matched the artefacts produced by the current
sources. Regenerated with `npm run hashes:build`; the release gate must run from
the regenerated file.

### F-30-02 — Underfunded `transfer` failed in the action phase (fixed)
`receive(TokenTransfer)` paid the receiver `internal_transfer` (0.02 TON) and the
`FeeTransfer` leg (0.05 TON) out of the wallet's own balance without first
checking that this account could fund them. TEP-74 requires the opposite:
a wallet that cannot guarantee its outgoing value "must immediately stop
executing the request and throw error". An explicit compute-phase guard now
rejects such requests.
Source: TEP-74, "Should be rejected if … there is no enough TON".

### F-30-03 — `FeeTransfer` bounce left the pending ledgers dirty (fixed)
`bounced(bounced<FeeTransfer>)` restored the jetton balance but kept
`pendingResponseFees` / `pendingResponses` / `pendingResponseReceivers` entries
for that query id, so a settled-looking record survived a leg that never landed.
The bounce now clears all three records for the query id.

### F-30-04 — Fee legs are funded by the wallet, not by the inbound value (fixed)
The residual of the inbound message used to stay on the sender wallet instead
of being refunded. The reference mode-64 forwarding turned out to be
infeasible for this contract: TON allows only ONE remaining-value action per
transaction, so forwarding the whole inbound value with the internal_transfer
leg while also paying the 0.05 TON `FeeTransfer` leg fails with action exit
code 37 (verified in the sandbox, commit `5dcae47`). The final design keeps
both legs balance-funded (F-19) and returns the explicit residual — inbound
value minus the 0.07 TON legs minus a 0.02 TON gas headroom — to
`response_destination` as the final `excesses` action, sent with
`SendPayGasSeparately | SendIgnoreErrors` (the same mode combination the Q-03
invariant approves for the `BurnConfirmed` leg). Regression coverage:
`tests/f30_04_fee_funding.test.ts` (on-chain refund assertion + source
assertions). The F-19 structural check was narrowed to the fee send itself,
preserving its meaning: a dropped `FeeTransfer` would still be forbidden from
silently ignoring delivery errors.
### F-30-05 — `scripts/deploy.js` is a compatibility shim (no change required)
`scripts/deploy.js` is an 18-line entry point that spawns `scripts/deploy_all.ts`
through `tsx` and holds no deployment logic of its own; no `package.json` script
references it. It is kept only for the historical `node scripts/deploy.js`
invocation and can be deleted once that call path is dropped.

## Post-audit fixes — second pass (same day, against the TON documentation)

Three defects found while re-verifying the claims in the table above. Each fix
carries the specification it restores.

| ID | File | Defect | Fix | Source |
|----|------|--------|-----|--------|
| Q-01 | `contracts/quasar.tact` (`receive(msg: ProposeContent)`) | A `0x01` off-chain content cell with no URI was accepted; TEP-64 defines that layout as `0x01 ++ ASCII URI`, so the staged value was unusable while the receiver still reported success. | The prefix byte is now read from a bounds-checked slice, a cell shorter than one byte is rejected, and an off-chain cell must carry a URI payload. | [TEP-64](https://github.com/ton-blockchain/TEPs/blob/master/text/0064-token-data-standard.md) |
| Q-02 | `contracts/quasar.tact` (`_workchainOf`) | The helper skipped the two TL-B tag bits and then read `anycast`+`workchain` unconditionally — valid only for `addr_std$10`. For `addr_none$00` / `addr_var$11` it reported workchain 0, so `provide_wallet_address` about an unaddressable owner returned a derived wallet address instead of `addr_none`. | The tag is now checked (`addr_std$10` only, anycast absent, at least 3 bits available); every other form returns `null` and takes the documented `addr_none` reply path. | [TEP-89](https://github.com/ton-blockchain/TEPs/blob/master/text/0089-jetton-wallet-discovery.md) |
| Q-03 | `contracts/quasar.tact` (`receive(msg: BurnNotification)`) | `BurnConfirmed` was sent with `value: 0` and a bare `SendIgnoreErrors` (mode 2) — base mode 0 with no `SendPayGasSeparately` makes the final value negative, so the action failed with exit code 37 and was silently swallowed, leaving the wallet's `pendingBurnResponses` ledger uncleaned. | The leg now uses `SendPayGasSeparately \| SendIgnoreErrors`. | [Message modes cookbook](https://docs.ton.org/v3/documentation/smart-contracts/message-management/message-modes-cookbook) |

Regression coverage: `tests/ton_doc_conformance_fix_2026_09_30.test.ts`
(on-chain compute-phase assertions for Q-01/Q-02 — the Q-02 test drives the real
`provide_wallet_address` reply and reads the `wallet_address` tag bits — plus a
structural assertion for Q-03).

Storage-fee guidance re-checked in the same pass: the documentation recommends
reserving against the measured maximum contract size rather than hardcoding a
coin amount, and warns that a balance below `freeze_due_limit` freezes the
account and breaks transaction chains. The repository keeps a fixed
`QUASAR_STORAGE_RESERVE = 0.05 TON`, which is a deliberate, documented trade-off
— see the "Still intentionally open" note in `docs/AUDIT_STATUS.md`.
Source: [Transaction fees](https://docs.ton.org/v3/documentation/smart-contracts/transaction-fees/fees)
