# TEP-64 — управляемые и on-chain метаданные (issue #58)

Дата: 2026-09-28. Основание: <https://github.com/ton-blockchain/TEPs/blob/master/text/0064-token-data-standard.md>
и <https://docs.ton.org/contracts/standard/tokens/metadata>.

## 1. Что было

`QuasarMaster.init(owner, content, walletCode)` хранил `content: Cell`, а
`get_jetton_data()` возвращал его как `jetton_content`. Значение собиралось
только как off-chain: `beginCell().storeUint(0x01, 8).storeStringTail(url)`.

Проблема: content входит в init data, а обработчика его изменения в контракте не
было. Ошибка в URL метаданных становилась неисправимой, при том что миграция кода
кошелька (`ProposeWalletCode` → «Apply Wallet Code») уже существовала.

## 2. Триayout-а TEP-64 (проверено по стандарту)

| Layout | Первый байт | Полезная нагрузка |
|---|---|---|
| off-chain | `0x01` | ASCII URI JSON-документа с метаданными |
| on-chain | `0x00` | словарь key/value, ключ = `sha256(имя атрибута)` |
| semi-chain | `0x00` | тот же словарь, но обязателен ключ `uri` |

Значения в словаре — строки в формате **snake**: ячейка несёт первый фрагмент,
остаток сцеплен через первую дочернюю ячейку рекурсивно (`SnakeData ~n`).

## 3. Что добавлено в контракт

* `message ProposeContent { newContent: Cell }` — только owner, при
  `aiFullAutonomy` запрещено;
* `receive("Cancel Content")` — отмена до подтверждения;
* `receive("Apply Content")` — применяет метаданные только после
  `ownerTransferDelay` (48 ч), по той же схеме, что миграция кода кошелька;
* поля `pendingContent: Cell?` и `contentAt: Int`;
* get-методы `get_pending_content()` и `get_content_at()`.

В `receive(ProposeContent)` на цепи проверяется только первый байт (`0x00` или
`0x01`): owner-supplied словарь намеренно непрозрачен, а его декодирование в
receive-фазе поставило бы неограниченный цикл в путь сообщения.

## 4. Общий модуль `scripts/lib/tep64.ts`

Собирает и разбирает все три layout-а, чтобы деплой, тесты и индексатор
использовали одну реализацию, а не самодельные ячейки:

`buildOffchainContent`, `buildOnchainContent`, `buildSemiChainContent`,
`parseContent`, `contentLayout`, `fieldKeyHash`, `reverseFieldKey`,
`toSnakeCell`, `fromSnakeCell`, `assertRequiredFields`, `assertDecimalsConsistent`.

## 5. Preflight в `scripts/deploy_all.ts`

Перед записью в init data:

1. `JETTON_METADATA_URL` резолвится и содержит `name`/`symbol`/`decimals`/`image`;
2. `decimals` из метаданных совпадает с множителем `10**CONFIG.decimals`,
   который использует минт (`assertDecimalsConsistent`) — иначе все балансы
   уезжали бы на порядок;
3. `JETTON_CONTENT_LAYOUT` = `offchain` (по умолчанию) | `onchain` | `semichain`;
4. собранная ячейка читается обратно (`parseContent`) — round-trip до деплоя;
5. после деплоя `get_jetton_data().jetton_content` сверяется по хешу с
   претендующей ячейкой.

Примечание про размер: snake-фрагмент ограничен 1023 битами ячейки, но ячейки
заполняются целыми байтами, поэтому модуль режет значение на 127-байтовые
фрагменты (1016 бит).

## 6. Тесты

`tests/tep64_content.test.ts`:

* round-trip всех трёх layout-ов, включая значение длиннее одной ячейки (2500 байт);
* ключ словаря действительно равен `sha256(имени атрибута)`;
* неизвестный префикс → `unknown`, без угадывания;
* `assertRequiredFields` / `assertDecimalsConsistent` на несоответствии;
* задеплоенный мастер отдаёт ровно ту ячейку, что лежит в init data;
* `ProposeContent` только ставит в очередь, `Apply Content` до истечения 48 ч
  не меняет метаданные, после — применяет и очищает `pendingContent`;
* `Cancel Content` очищает предложение; не-owner не может поставить его в очередь.

Инварианты также закреплены в `scripts/security_check.ts`.
